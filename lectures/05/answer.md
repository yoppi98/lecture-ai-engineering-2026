## 宿題

- **取り組んだレベル：基礎**

### やったこと

`app/config.py`の`RAG_TOP_K`を5から2に変更した。

検索件数を減らすことで入力トークン数とAPIコストが削減できると考え、回答の正確性、検索ツールの呼び出し回数、応答時間、トークン数、推定APIコストを比較した。

### 比較した質問と固定条件

モデルは`gemini-3.5-flash-lite`、検索対象は第1〜3回の本講義資料とした。変更した設定は`RAG_TOP_K`のみである。

2種類の質問を使用した。

1. 単一ページ中心：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」
2. 複数ページ：「コンパクションとセッションをまたぐメモリの違いは？ 日々のメモは全部長期メモリになる？」

質問2については、TOP_K=2の実行時に疑問符の直前に空白が入っていたため、質問文が厳密には一致していない。

### 結果

**質問1：LoRAとQLoRA**

| 項目 | TOP_K = 5 | TOP_K = 2 |
|---|---|---|
| 回答 | 正答 | 正答 |
| 引用ページ | 第2回 p.51, 52 | 第2回 p.51, 52 |
| 検索ツール呼び出し | 1回 | 1回 |
| 応答時間 | 2.13秒 | 4.99秒 |
| 入力トークン | 3,028 | 1,741 |
| 出力トークン | 197 | 197 |
| モデル応答回数 | 2 | 2 |
| 推定APIコスト | $0.001401 | $0.001015 |

どちらも同じ検索語`LoRA 固定 学習 QLoRA 加える`を使用し、正しい回答を生成できた。

TOP_Kを5から2に変更すると、入力トークン数は約42.5%、推定APIコストは約27.6%削減された。一方、応答時間は2.13秒から4.99秒に増加した。

**質問2：コンパクションと長期メモリ**

| 項目 | TOP_K = 5 | TOP_K = 2 |
|---|---|---|
| 回答 | 正答 | 正答 |
| 引用ページ | 第3回 p.13, 39, 40, 65 | 第3回 p.39, 40, 65 |
| 検索ツール呼び出し | 1回 | 2回 |
| 応答時間 | 7.22秒 | 8.02秒 |
| 入力トークン | 2,482 | 3,396 |
| 出力トークン | 441 | 418 |
| モデル応答回数 | 2 | 3 |
| 推定APIコスト | $0.001847 | $0.002064 |

TOP_K=5では1回の検索で正答できたが、TOP_K=2では2回の検索が必要になった。

TOP_K=2の検索語は以下の通りだった。

- 1回目：`コンパクション セッション メモリ 長期メモリ`
- 2回目：`日々のメモ 長期メモリ`

その結果、TOP_K=2では入力トークン数が約36.8%、推定APIコストが約11.7%増加した。

### 改善した例と、残る失敗・制約

単一ページを中心とする質問では、TOP_Kを減らしても必要な根拠を取得でき、回答の正確性を維持しながらコストを削減できた。

一方、複数ページの情報が必要な質問では、TOP_K=2で追加検索が発生し、かえってトークン数とコストが増加した。検索件数を減らしたことで追加検索が必要になった可能性があるが、原因の特定にはさらに検証が必要である。

また、TOP_K=2の実行中に503エラーも発生した。これはモデルAPI側の問題であり、回答品質の評価には含めなかった。

今回の比較は各条件1回の成功例に基づいているため、応答時間の違いにはAPIの混雑や実行環境による変動も含まれる可能性がある。

### 気づき・疑問

今回の実験から、検索件数を減らすことが必ずしもトークン数やコストの削減につながらないことが分かった。特に複数ページの情報が必要な場合、検索件数が少なすぎると追加のツール呼び出しが発生する可能性がある。

今後は、質問の複雑さや検索結果の関連度に応じてTOP_Kを動的に調整する方法を試したい。また、複数回測定を行い、平均応答時間やコストを比較することで、より信頼性の高い評価ができると考える。
